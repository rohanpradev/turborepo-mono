## Application and tooling changes

- Next error boundaries use the stable `retry` API to refetch failed Server
  Component data. Global fallbacks accept unknown thrown values and retain
  their standalone document titles. Refresh buttons issue one recovery action.
- Stripe's Payment Element uses `onReady` and `onLoadError`. Submission waits
  for the element, and failed loading offers an element reload within the same
  Checkout session.
- Both Zustand stores use guarded browser storage with a per-visit memory
  fallback. Denied storage no longer prevents hydration; failed writes/removals
  cannot revive stale cart or delivery details during the visit.
- Removed redundant Turbopack aliases. Next resolves the existing TypeScript
  paths directly; Knip 6.43 can inspect the composed configuration without
  unresolved-directory exceptions.
- Tooling type-check cache inputs include the application/package sources and
  manifests imported by operational scripts. The task waits for Prisma
  generation and uses Turbo's `dependencyOutputs` hashing after generated
  contracts exist. Previously, an imported backend edit could reuse a stale
  successful tooling check.
- Biome explicitly enables the new boolean-sort-comparator and obsolete HTML
  attribute checks. Biome remains the formatter because `bun fmt` does not
  implement the repository's Biome policy.
- Standalone smoke checks now request both AVIF and WebP image transformations,
  alongside health, pages, assets, sitemap outage behavior, streaming, and
  uncached stock-state checks.

## Prisma migration and database proof

The upgrade uses the target package's cumulative rc.17→rc.21 recipes and
official converters, rather than changing version strings alone. It updates
`contractFromJson` client construction, `TimestampTemporal` names, stored
contracts, content-addressed snapshots/references, generated types, and the
baseline's stronger operation checks. The 12 baseline DDL operations and their
parameters remain unchanged.

PostgreSQL already permitted null elements in product variant arrays. The new
contract describes them as `String?[]`; serialization filters null elements at
the service boundary so the public catalog still returns `string[]`.

On disposable PostgreSQL 18.6, the old dependency pair deployed its original
baseline first. Fixtures included normal and nullable-array products, fixed
timestamps, categories, and pending/publishing/published outbox records. The
new pair strictly verified and adopted that database, then deployed and
verified successfully. Business data and the original migration ledger were
byte-for-byte unchanged. Deployment performed no operations after adoption.
A separate empty database applied all 12 converted baseline operations and
passed verification. Repeated deployment on both databases performed no
operations.

The storage hash changes from `65a2e3fdd7d073ff6b91467777940a26a791ca4982ed6903bca77195f39927e7`
to `66e9d562ab1892e4a2ec1137b5b9418c4e93f38e847eef96d88482a99eeb68fb`.
Existing installations require the explicit verified adoption procedure before
starting the new application. Deployment does not automatically sign databases.
See [the exact migration and rollback procedure](../packages/product-db/UPGRADE_RC21.md).

## Deployment verification improvements

CI builds and loads an AMD64 application image, runs restricted production
checks, and only then permits multi-platform publication with provenance and
SBOMs. The image test exercises production imports/health for services and web
rendering, static assets, and native image optimization under an arbitrary
non-root UID, a read-only root, dropped capabilities, and no external network.
Both ARM64 and AMD64 image execution were checked locally on the development
host, including AMD64 through emulation.

The actual backend entry commands were also started against the disposable
dependencies on ARM64. Product and order readiness reached 200 with their
database and Kafka dependencies ready. Payment liveness reached 200 and its
database was ready; overall readiness correctly stayed 503 without Stripe keys
and a webhook signing secret, with payment workers disabled. The temporary
application and database containers were removed after verification.

Integration database images use the same version/digest as CI. Kafka uses
separate internal and external listeners so metadata requests work both inside
the container and from host tests; readiness checks actual metadata, rather
than only an open socket.

The first hosted integration run exposed a runner compatibility problem before
tests could start. MongoDB 8.3.13 rejects the `7.0.0-1017-azure` kernel currently
used by both GitHub's Ubuntu 24.04 and 26.04 images, because its version check
does not recognize Ubuntu's upstream kernel patch level. The
[runner maintainers reproduce this exact failure and recommend Ubuntu 22.04](https://github.com/actions/runner-images/issues/15005),
whose current runner kernel is 6.8. Only the database integration job temporarily
selects `ubuntu-22.04`; quality and application image jobs keep `ubuntu-latest`.
The MongoDB security patch, image digest, health checks, and integration tests
remain intact. Restore the default runner after a published compatible MongoDB
patch containing [SERVER-131779](https://jira.mongodb.org/browse/SERVER-131779)
passes hosted integration. MongoDB 8.3.14 is the planned backport, but was not
published when checked on 29 October. GitHub's Ubuntu 22.04 runner
[retires on 17 April 2027](https://github.com/actions/runner-images/issues/14254),
so this compatibility pin must be removed before that retirement.

Kubeconform now consumes the pinned Gateway API and monitoring custom-resource
schemas instead of skipping those resources. All 12 profile/version combinations
validate with zero skipped resources. A deliberately invalid HTTPRoute is
rejected by its schema.
